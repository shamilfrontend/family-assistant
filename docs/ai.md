# AI-ассистент

Провайдер и подфазы — в [README.md](../README.md). HTTP — в [api.md](api.md). Черновики и маски — в [data-model.md](data-model.md).

Клиент с DeepSeek не разговаривает. Ключ (`DEEPSEEK_API_KEY`) только на бэкенде.

## Вызов

- Протокол: Chat Completions, OpenAI-совместимый SDK, `base_url`: `https://api.deepseek.com`
- Модель: `deepseek-chat`
- Температура: `0.3`. Ответы короткие, бытовые.
- Таймаут запроса к провайдеру: **30 с**. Дальше — как деградация (`llm_unavailable`).
- Язык ответа — язык последнего сообщения пользователя, по умолчанию русский.

Tools на стороне сервера. Модель **не пишет в БД**. Tool = предложение операции → строка `AiDraft` со статусом `PENDING`, `messageId` = assistant-сообщение этого ответа. Применение — только `POST /chats/:id/drafts/:draftId/apply` с проверкой роли.

## Сборка контекста

Сервер, не клиент. Порядок сообщений в запрос к модели:

1. System: роль, запреты, текущая подфаза, пояс семьи, сегодняшняя дата в этом поясе. В БД не пишется.
2. Facts: выборка **по роли** под вопрос (не вся база).
3. История: последние **20** сообщений этого чата (`USER` и `ASSISTANT`; без полных номеров документов; если пользователь сам написал номер — не копировать в Facts из БД, в историю чата не фильтровать ретроактивно).
4. Текущее user-сообщение.

### Facts по подфазам

| Подфаза | В контекст | Не в контекст |
| --- | --- | --- |
| 1.3 | Члены: id, имя, роль. События сегодня и на 7 дней (ребёнок — свои как участник). Покупки (название, категория, куплено, кто добавил). | Номера документов, здоровье, чужие чаты |
| 1.4 | + открытые дела (исполнитель, срок). + документы: тип, владелец, дата окончания, `expiresSoon`. | `Document.number` |
| 1.5 | + здоровье в рамках роли; аллергии из `Member.allergies` | События типа `DOCTOR` как «приёмы» |

Ребёнок: те же правила RBAC, что API. Промптом роль не обойти: лишних строк в Facts нет.

Если вопрос про здоровье до 1.5 — ответ шаблоном «здоровье ещё не подключено», без вызова лишних выборок.

## Tools (предложение, не запись)

Имена — для модели. Сервер после tool call создаёт `AiDraft` и возвращает модели `{ draftId, operation }`.

| Tool | Подфаза | Payload черновика |
| --- | --- | --- |
| `propose_create_purchase` | 1.3 | `{ title, category? }` → category по умолчанию `OTHER` |
| `propose_create_event` | 1.4 | `{ title, type, startsAt, endsAt?, allDay, participantIds, recurrence?, remindInUi? }` |
| `propose_create_task` | 1.4 | `{ title, assigneeMemberId, dueAt, recurrence? }` |
| `propose_complete_task` | 1.4 | `{ taskId }` |
| `propose_mark_purchase_bought` | 1.4 | `{ purchaseId }` |

Нет tools на удаление, документы, мед. записи, смену ролей. Tools события и дела ребёнку в schema всё равно отдавать нельзя: сервер режет список tools по роли (1.3: только покупка; ребёнок в 1.4 — покупка, отметка купленного, complete своего дела; без create event/task).

Составной запрос («молоко и хлеб») — несколько tool call → несколько черновиков с одним `messageId`. Один черновик = одна операция. TTL 1 час.

Apply по роли:

- `CREATE_PURCHASE`, `MARK_PURCHASE_BOUGHT` — оба
- `CREATE_EVENT`, `CREATE_TASK` — только взрослый; ребёнок — `forbidden`
- `COMPLETE_TASK` — ребёнок только своё дело

Модель просит подтверждение в тексте и опирается на кнопки UI (id черновика). Фраза пользователя «да» apply **не** вызывает — только HTTP apply.

## Имена

Сопоставление только с `Member.name` (без регистра), без уменьшительных и догадок.

- 0 совпадений — сказать, что такого члена нет; черновик на человека не создавать.
- 1 — использовать этот `id`.
- больше 1 — уточнить списком `{ id, name }`, не брать первого.

## Деградация

LLM недоступна, таймаут (30 с), 5xx провайдера: HTTP `503` `llm_unavailable`. Сообщение пользователя можно не сохранять. В данные не писать. UI: «Ассистент сейчас не отвечает».

## Запреты в system

- Не ставить диагнозы и не давать назначения.
- Не выводить и не просить полный номер документа.
- Не утверждать, что запись уже создана, пока черновик не `APPLIED`.
- Приёмы — только `HealthRecord` `APPOINTMENT`, не событие `DOCTOR`.
- Не отвечать данными другой роли, даже если пользователь просит.
